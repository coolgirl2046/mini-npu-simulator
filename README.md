# Mini NPU Simulator

MAC(Multiply-Accumulate, 곱하고 누적해서 더하기) 연산으로 입력 패턴이 십자가(Cross)인지 X인지 판별하는 Python 콘솔 프로그램입니다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `os`, `re`)만 사용합니다.

---

## 1. 실행 방법

- 필요 환경: Python 3.8 이상
- 폴더 구성

```
mini-npu/
├── main.py      # 메인 실행 파일
├── data.json    # 모드 2 입력 데이터 (main.py와 같은 폴더에 둔다)
└── README.md
```

- VS Code 터미널(또는 PowerShell)에서 `main.py`가 있는 폴더로 이동한 뒤 실행합니다.

```
python main.py
```

- 실행하면 모드를 선택합니다.
  - `1` 입력: 사용자 입력 모드(3×3). 필터 A, 필터 B, 패턴을 각각 3줄씩 공백으로 구분해 입력합니다.
  - `2` 입력: data.json 분석 모드. `main.py`와 같은 폴더의 `data.json`을 읽어 일괄 판정합니다.

## 2. 구현 요약

### 2-1. 데이터 구조
- 패턴과 필터는 `리스트 안의 리스트`(2차원 배열)로 저장합니다. `matrix[행][열]`로 특정 위치의 값을 읽고 씁니다.
- `make_matrix(n)`, `get_value()`, `set_value()` 함수로 n×n 배열 생성과 위치별 읽기/쓰기를 제공합니다.
- 크기를 고정하지 않으므로 3×3, 5×5, 13×13, 25×25를 모두 같은 코드로 처리합니다.

### 2-2. 라벨 정규화
data.json은 같은 의미를 서로 다른 표기로 씁니다. (expected는 `+`/`x`, 필터 키는 `cross`/`x`)
프로그램 안에서는 표준 라벨 `Cross`, `X` 두 가지만 쓰도록 `normalize_label()`에서 변환합니다.

| 원래 값 | 위치 | 표준 라벨 |
|---|---|---|
| `+` | expected | Cross |
| `x` | expected | X |
| `cross` | filter 키 | Cross |
| `x` | filter 키 | X |

앞뒤 공백 제거와 소문자 변환을 먼저 하므로 `" Cross "`, `"X"` 같은 표기도 같은 라벨로 처리됩니다.
해석할 수 없는 라벨은 프로그램을 멈추지 않고 해당 케이스만 FAIL로 처리합니다.

### 2-3. MAC 연산
`mac(pattern, filter)`는 이중 반복문으로 모든 위치 (i, j)를 돌며 `pattern[i][j] * filter[i][j]`를 누적합니다. NumPy 같은 벡터화 라이브러리는 쓰지 않습니다.
점수는 float로 반환합니다.

### 2-4. 동점 처리 정책 (epsilon)
`abs(score_a - score_b) < 1e-9`이면 동점으로 보고 `UNDECIDED`(모드 1에서는 "판정 불가")로 판정합니다.
그렇지 않으면 점수가 더 큰 쪽의 라벨로 판정합니다. 동점 판정은 expected와 같을 수 없으므로 FAIL로 집계합니다.

### 2-5. 오류 처리
- 모드 1: 한 줄의 숫자 개수가 3개가 아니거나 숫자로 바꿀 수 없는 값이 있으면 안내 문구를 출력하고 그 행렬을 처음부터 다시 입력받습니다.
- 모드 2: 아래 경우는 프로그램을 멈추지 않고 해당 케이스만 FAIL로 처리하고 사유를 남깁니다.
  - 키가 `size_N_idx` 형식이 아님
  - 해당 크기의 필터가 없음
  - expected 라벨을 해석할 수 없음
  - input이 정사각 숫자 배열이 아님
  - 키의 N과 input 실제 크기가 다름(크기 불일치)
- data.json 파일이 없거나 JSON 문법이 틀린 경우 안내 메시지를 출력하고 종료합니다.

### 2-6. 성능 측정
- `time.perf_counter()`로 MAC 함수 호출 구간만 측정합니다. 입력, 출력, 파일 읽기는 측정 구간에 포함하지 않습니다.
- 측정 전 1회 워밍업 호출을 하고, 이후 10회 반복 호출의 평균(ms)을 출력합니다.
- 측정용 패턴과 필터는 `generate_cross(n)`, `generate_x(n)` 함수로 만든 N×N 십자가/X를 사용해 크기만 다르고 조건은 같게 맞췄습니다.

### 2-7. 보너스 (선택 과제 중 1번 수행)
- **1차원 배열 최적화**: `flatten()`으로 2차원 배열을 길이 N²의 1차원 배열로 펼친 뒤 `mac_flat()`에서 반복문 1개로 계산합니다. 펼치는 작업은 측정 구간 밖에서 미리 해 두고, 2D와 같은 입력과 같은 반복 횟수로 비교합니다. 성능 표의 `1D 최적화(ms)` 열이 그 결과입니다.

## 3. 결과 리포트

> 아래 결과는 과제에서 제공한 원본 `data.json`으로 `python main.py` → `2`를 실행한 결과입니다.
> 성능 수치는 본인 PC(Windows, VS Code 터미널)에서 실행한 값이며, 실행할 때마다 조금씩 달라집니다.

### 3-1. 테스트 결과

| 케이스 | Cross 점수 | X 점수 | 판정 | expected | 결과 |
|---|---|---|---|---|---|
| size_5_1 | 0.9 | 0.8999999999999999 | UNDECIDED | X | FAIL |
| size_5_2 | 8.9 | 0.1 | Cross | Cross | PASS |
| size_13_1 | 0.3 | 14.700000000000008 | X | X | PASS |
| size_13_2 | 7.499999999999997 | 7.5 | UNDECIDED | Cross | FAIL |
| size_25_1 | 4.9 | 4.899999999999999 | UNDECIDED | X | FAIL |
| size_25_2 | 52.9 | 0.1 | Cross | Cross | PASS |

```
총 테스트: 6개
통과: 3개
실패: 3개

실패 케이스:
- size_5_1: 동점(UNDECIDED, |차이| < 1e-9) 규칙에 따라 FAIL
- size_13_2: 동점(UNDECIDED, |차이| < 1e-9) 규칙에 따라 FAIL
- size_25_1: 동점(UNDECIDED, |차이| < 1e-9) 규칙에 따라 FAIL
```

### 3-2. 실패 원인 분석

실패 원인을 "데이터/스키마 문제", "로직 문제", "수치 비교 문제"로 나눠 점검했습니다.

**(1) 라벨/스키마 문제 → 해당 없음**
- expected는 `+`/`x`, 필터 키는 `cross`/`x`로 표기가 다르지만, 정규화로 모두 `Cross`/`X`로 통일한 뒤 비교했습니다.
- 모든 키가 `size_N_idx` 형식이고, 패턴과 필터 크기도 모두 일치했습니다. 크기 불일치나 라벨 해석 실패로 FAIL이 된 케이스는 없습니다.
- 각 패턴의 expected도 실제 모양과 맞습니다. (size_5_1, size_13_1, size_25_1은 대각선 모양 = X, 나머지는 십자 모양 = Cross)

**(2) 로직 문제 → 해당 없음**
- 실패 3건의 점수를 손으로 계산해 보면, 프로그램 결과와 같습니다. MAC 계산 자체에는 오류가 없습니다.

**(3) 수치 비교 문제 + 필터 설계 → 실패 3건의 원인**
실패한 3건은 모두 **수학적으로 두 점수가 정확히 같은 경우**입니다. 필터 값이 그렇게 맞춰져 있기 때문입니다.

| 케이스 | Cross 필터 점수 계산 | X 필터 점수 계산 |
|---|---|---|
| size_5_1 (X 모양) | 가운데 칸 0.9 × 1 = 0.9 | 대각선 9칸 × 0.1 = 0.9 |
| size_13_2 (십자 모양) | 십자 25칸 × 0.3 = 7.5 | 가운데 칸 7.5 × 1 = 7.5 |
| size_25_1 (X 모양) | 가운데 칸 4.9 × 1 = 4.9 | 대각선 49칸 × 0.1 = 4.9 |

- 패턴과 필터가 겹치는 칸은 X와 십자의 교차점인 가운데 1칸뿐인데, 그 가운데 칸에 큰 값(0.9, 7.5, 4.9)을 넣어 반대쪽 필터 점수와 같아지도록 설계되어 있습니다.
- 그런데 컴퓨터는 0.1, 0.3 같은 소수를 2진수로 정확히 표현하지 못합니다. 그래서 0.1을 9번 더하면 0.9가 아니라 `0.8999999999999999`가 됩니다.
- epsilon 없이 `>`로 비교하면, 이 아주 작은 오차(약 1e-16) 때문에 승패가 갈립니다. 실제로 계산해 보면 세 케이스 모두 **expected와 반대 라벨**로 판정됩니다. (size_5_1 → Cross, size_13_2 → X, size_25_1 → Cross)
- 즉 epsilon 정책이 없었다면 "계산 오차가 우연히 정한 엉터리 답"이 나왔을 것입니다. epsilon(1e-9)을 적용해 차이가 오차 수준이면 동점으로 보고 UNDECIDED로 판정했습니다.
- 과제 규칙상 UNDECIDED는 expected와 다르므로 FAIL로 집계합니다. 따라서 이 FAIL 3건은 프로그램 버그가 아니라, **판별할 수 없는 입력을 억지로 판정하지 않도록 한 비교 정책이 의도대로 동작한 결과**입니다.

**개선 방향**
- 이 3건을 PASS로 만들려면 비교 정책을 바꾸는 것이 아니라 필터를 바꿔야 합니다. 예를 들어 가운데 칸 가중치를 낮추면 모양이 다른 패턴끼리 점수가 같아지지 않습니다.
- epsilon을 없애거나 아주 작게 줄여 PASS를 만드는 것은 우연에 기대는 것이고, 실제로는 3건 모두 오답이 되므로 올바른 해결이 아닙니다.

### 3-3. 성능 분석 (평균/10회)

| 크기 | 평균 시간(ms) | 1D 최적화(ms) | 연산 횟수(N²) |
|---|---|---|---|
| 3×3 | 0.0041 | 0.0013 | 9 |
| 5×5 | 0.0149 | 0.0049 | 25 |
| 13×13 | 0.0229 | 0.0068 | 169 |
| 25×25 | 0.0955 | 0.0820 | 625 |

### 3-4. 시간 복잡도 분석: O(N²)

- MAC은 N×N 배열의 모든 칸을 한 번씩 곱하고 더하므로 곱셈과 덧셈이 각각 N²번 일어납니다. 그래서 시간 복잡도는 **O(N²)**입니다.
- 13×13 → 25×25에서 연산 횟수는 169 → 625로 약 3.7배, 측정 시간은 0.0229 → 0.0955ms로 약 4.2배 늘었습니다. 큰 크기에서는 시간이 N²에 가깝게 비례해 늘어납니다.
- 반면 3×3 → 25×25 전체로 보면 연산 횟수는 약 69배인데 시간은 약 23배만 늘었습니다.
- 이유는 크기와 상관없이 매번 드는 고정 비용(함수 호출, 반복문 준비, 변수 초기화) 때문입니다. 3×3처럼 작은 크기에서는 실제 곱셈보다 이 고정 비용 비중이 커서 시간이 상대적으로 크게 보입니다.
- 또 5×5 → 13×13 구간은 연산 횟수가 약 6.8배 늘었는데 시간은 약 1.5배만 늘었습니다. 1회 연산이 수 마이크로초(μs) 수준이라 10회 평균에는 운영체제의 다른 작업 같은 잡음이 크게 섞이기 때문으로 보입니다. 더 정확히 보려면 반복 횟수를 늘리거나(예: 1000회) 더 큰 N에서 측정하면 됩니다.
- 1D 최적화는 모든 크기에서 2D보다 빨랐습니다. 반복문이 1개로 줄고, `pattern[i][j]`처럼 리스트를 두 번 찾아 들어가던 것이 `pattern[k]` 한 번으로 줄었기 때문입니다.
- 다만 크기가 커질수록 차이가 줄었습니다(3×3에서 약 68% 빠름 → 25×25에서 약 14% 빠름). 작은 크기에서는 줄어든 반복문 준비 비용의 효과가 크고, 큰 크기에서는 N²번의 곱셈·덧셈 자체가 시간 대부분을 차지하기 때문입니다.
- 1D 역시 N²번 곱해야 하므로 복잡도는 O(N²) 그대로이고, 최적화는 같은 차수 안에서 상수(한 번 계산에 드는 비용)만 줄인 것입니다.
- 실제 AI 모델은 이런 MAC를 수억 번 반복합니다. CPU처럼 하나씩 순서대로 처리하면 시간이 N²에 비례해 늘어나기 때문에, 많은 MAC를 동시에 처리하는 NPU가 필요합니다.
